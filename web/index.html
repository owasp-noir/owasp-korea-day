무엇을 고치나요

Noir는 소스 코드를 읽고, 그 서비스에 어떤 주소가 열려 있는지 찾아 줘요. 이런 주소를 엔드포인트라고 불러요. /login, /api/orders 같은 것들이에요.

찾은 엔드포인트에는 "여기는 결제", "여기는 웹훅" 같은 태그를 붙여요. 보안 점검하는 사람이 어디부터 볼지 고르기 쉬워지거든요.

그런데 가끔 태그를 빠뜨려요. 카카오페이로 예를 들어 볼게요. 카카오페이는 결제가 끝나면 pg_token이라는 값을 붙여서 우리 서버로 돌려보내요. 그래서 카카오페이를 붙인 서버에는 보통 이런 코드가 있어요.

app.get("/kakaoPaySuccess", function (req, res) {
  const pgToken = req.query.pg_token;

  // 받은 pg_token으로 카카오페이에 결제 승인을 요청해요.
  ...
});

Noir로 스캔하면 주소와 받는 값을 잘 찾아요. 그런데 결제 태그가 안 붙어요.

GET /kakaoPaySuccess?pg_token=

Noir가 pg_token이라는 이름을 모르기 때문이에요. Noir가 아는 이름은 대부분 해외 서비스 것이거든요. 이 이름을 추가하면 결과가 이렇게 바뀌어요.

GET /kakaoPaySuccess?pg_token=
  ○ tags: payment

실제로 카카오페이를 붙인 공개 저장소 다섯 곳을 스캔해 봤어요. pg_token을 받는 주소 6개 중 3개에 결제 태그가 없었고, 이 단어를 추가하니 6개 모두에 붙었어요. 오늘은 이렇게 국내 서비스에서만 쓰는 이름을 룰에 추가해요.

룰 파일은 이렇게 생겼어요

태그를 붙이는 규칙은 src/tagger/rules/ 폴더에 파일로 들어 있어요. 결제, 웹훅, 관리자처럼 태그 하나에 파일 하나예요. 결제 룰을 간단히 줄이면 이래요.

key: payment
match:
  any:                        # 아래 중 하나라도 맞으면 태그를 붙여요
    - path_segment: [payment, checkout, billing, paypal, stripe]
    - param:
        name: [card_number, cvv, payment_method]
examples:
  match:                      # 태그가 붙어야 하는 예
    - { method: POST, url: /api/checkout }
  no_match:                   # 태그가 붙으면 안 되는 예
    - { url: /api/orders }

네 가지만 알면 돼요.

이름 하는 일 예
path_segment 주소를 / - _ .에서 잘라 조각으로 나눈 다음, 그 조각이 목록에 있는지 봐요. 대문자와 소문자는 구분하지 않아요. /kakao-pay/ready는 kakao, pay, ready로 나뉘어요. /kakaopay/ready는 kakaopay, ready로 나뉘어요.
param의 name 요청에 담겨 오는 값의 이름을 봐요. 대문자와 소문자, -, _는 따지지 않아요. pg_token, pgToken, pg-token을 모두 같은 이름으로 봐요. 하나만 적으면 돼요.
url_contains 주소를 조각으로 나누지 않고, 이 글자가 주소 어딘가에 들어 있는지 봐요. 소문자로 적어요. sign-in처럼 -나 _가 들어간 말은 path_segment로 찾을 수 없어서 이걸 써요.
examples 룰이 제대로 동작하는지 확인하는 예시예요. PR을 올리면 자동 검사가 하나씩 돌려 봐요. 테스트 코드를 따로 쓸 필요가 없어요.

더 많은 조건은 룰 폴더의 README에 있어요.

따라 하기

아래 예시는 위에서 본 카카오페이예요. 여러분은 첫 단계에서 고른 과제에 맞게 바꿔서 따라 하면 돼요.

과제 고르기

과제 목록에서 하나를 골라 열어요. 과제는 크게 두 가지예요.

종류 어떤 과제 이 가이드와 다른 점
있는 룰에 단어 추가하기 결제, 로그인, 본인인증처럼 이미 있는 태그에 국내 서비스의 단어를 넣어요. 없어요. 아래 순서 그대로 하면 돼요.
새 룰 파일 만들기 검색, 주문, 프로필, 게시판처럼 아직 없는 태그를 만들어요. 2단계에서 파일을 새로 만들어요.

골랐으면 과제에 댓글을 남겨요. 댓글 칸은 과제 화면 맨 아래에 있어요.

  • 과제에 "여러 사람이 이 이슈 하나를 같이 씁니다"라고 적혀 있으면, 추가할 단어를 정해 "naverpay 제가 할게요"처럼 적어요. 다른 분이 이미 맡은 단어는 피해 주세요.
  • 그런 말이 없으면 한 사람이 맡는 과제예요. "제가 할게요"라고 적어요. 이미 댓글이 달려 있으면 다른 과제를 골라 주세요.

추가할 이름은 기억에 기대지 말고, 그 서비스의 공식 문서나 공식 샘플 코드에서 확인해 주세요. 확인한 주소는 댓글에 같이 적고, 나중에 PR에도 붙여요.

과제에 내 댓글이 달렸어요. 단어를 추가하는 과제라면 단어와, 그 단어를 확인한 주소도 적어 뒀어요.

고칠 파일 열기

고칠 파일을 GitHub에서 열어요. 결제 룰이라면 payment.yml이에요. 다른 파일이라면 주소창에 https://github.com/owasp-noir/noir/blob/main/을 적고, 그 뒤에 과제에 적힌 경로(src/tagger/rules/webhook.yml 같은 것)를 붙여서 열어요. 파일이 열리면 오른쪽 위에 있는 연필 아이콘을 눌러요.

이 저장소를 직접 고칠 권한은 없어서, GitHub가 내 계정에 복사본을 만들자고 해요. 이걸 포크라고 해요. Fork this repository를 누르면 복사본이 생기고, 거기서 고치게 돼요.

새 룰 파일을 만드는 과제라면 새 파일 만들기를 열어요. 맨 위 이름 칸에 과제에 적힌 파일 이름(search.yml 같은 것)을 넣고, 아래 틀을 붙여 넣은 다음 내 과제에 맞게 바꿔요. 틀은 알림 태그를 예로 든 거예요.

key: notification
name: Notification Tagger
summary: Identifies notification endpoints
order: 400
tag:
  tagger: Notification
  description: Notification endpoint; review access.
match:
  any:
    - path_segment: [notification, notifications]
examples:
  match:
    - { url: /notifications }
    - { method: POST, url: /api/notification/read }
  no_match:
    - { url: /blog/posts }
    - { url: /catalog }
  • key는 파일 이름과 같아야 해요. search.yml이면 search예요.
  • order에는 과제에 적힌 숫자를 써요.
  • name, summary, tag 아래 두 줄은 영어로 짧게 적어요. description에는 이 태그가 붙은 주소에서 무엇을 점검해야 하는지 적어요.
  • match에는 조건을, examples에는 태그가 붙어야 하는 예(match)와 붙으면 안 되는 예(no_match)를 적어요.

틀을 바꾸기 전에 3단계와 4단계의 설명을 읽어 보세요. 단어를 고르는 법과 no_match를 쓰는 법은 새 파일에서도 같아요. 다 바꿨으면 5단계로 넘어가요.

파일 내용을 고칠 수 있는 편집 화면이 열렸어요.

단어 추가하기

match 아래에서 알맞은 목록을 찾아 단어를 추가해요. 카카오페이 예시에서는 이름 하나를 넣어요.

     - param:
         name: [card_number, cc_number, cvv, cvc, cvv2, cvn, csc, security_code,
                ...
-               iban, routing_number, sort_code]
+               iban, routing_number, sort_code, pg_token]
  • 위 상자에서 -로 시작하는 줄이 고치기 전, +로 시작하는 줄이 고친 뒤예요. 맨 앞의 +, - 기호와 ...은 줄인 표시라서 입력하지 않아요.
  • 같은 이름의 목록이 두 개 있으면 위쪽 목록에 넣어요. 아래쪽 목록은 all: 안에 있어서, 다른 조건도 같이 맞아야 태그가 붙어요.
  • 띄어쓰기는 스페이스로 하고, 윗줄과 줄을 맞춰요. 탭 키는 쓰지 않아요.
  • 단어는 쉼표로 이어서 ] 앞에 넣어요. ]는 맨 끝에 하나만 있어야 해요.
  • 이름은 한 가지 모양으로만 적어요. pg_token을 넣으면 pgToken도 같이 잡혀요.
  • path_segment에는 -, _, ., /가 들어간 단어를 넣을 수 없어요. kakao_pay가 아니라 kakaopay로 적어요.
  • 너무 흔한 단어는 넣지 않아요. token만 넣으면 로그인 토큰을 받는 요청까지 전부 결제로 잡혀요.

화면 위쪽의 Preview 탭을 누르면 바뀐 줄만 초록색과 빨간색으로 보여요. 내가 고치려던 줄만 바뀌었어요.

예시 추가하기

같은 파일 아래쪽에 있는 examples에 예시를 추가해요. match에는 방금 넣은 단어 덕분에 새로 태그가 붙는 요청을 적어요. no_match에는 비슷해 보여도 태그가 붙으면 안 되는 요청을 적어요.

 examples:
   match:
     ...
+    - { url: /kakaoPaySuccess, params: [{ name: pg_token }] }
   no_match:
     ...
+    - { url: /auth/refresh, params: [{ name: token }] }

여기서 제일 중요한 건 no_match예요. 태그는 붙이기보다 엉뚱한 데 안 붙게 하기가 더 어렵거든요. "이 단어를 넣으면 어떤 주소가 잘못 걸릴까?" 한 번 생각해 보고, 떠오른 주소를 적어 주세요.

예를 하나 들게요. 전자정부 표준프레임워크에는 /sym/cal/EgovAdministDayCalendar.do라는 주소가 있어요. 여기서 Administ는 "관리자"가 아니라 "행정"이에요. admin이라는 글자가 들어 있다고 관리자 태그를 붙이면 틀려요. 이런 건 그 서비스를 써 본 사람이 제일 잘 알아요.

추가한 단어마다 match 예시를 하나씩 넣었어요. no_match 예시도 하나 이상 넣었어요. 원래 있던 예시는 지우지 않았어요.

PR 올리기

이제 고친 내용을 반영해 달라고 요청할 차례예요. 이 요청을 PR(풀 리퀘스트)이라고 해요.

화면 오른쪽 위의 Commit changes…를 눌러요. 창이 뜨면 무엇을 고쳤는지 한 줄 적고 Propose changes를 눌러요. 바뀐 내용을 보여 주는 화면으로 넘어가요. 제목과 내용을 적는 칸이 바로 보이면 거기에 적으면 되고, 안 보이면 Create pull request를 한 번 눌러 칸을 열어요.

제목에는 무엇을 바꿨는지 한 줄로 적어요. 제목과 내용 모두 한국어로 써도 돼요. 영어로 쓴다면 아래 예시를 조금 바꾸면 돼요.

feat: tag KakaoPay approval redirects as payment

내용은 아래 틀에서 내 과제에 맞게 바꿔 적어요.

## What
Adds `pg_token` to the payment rule's parameter names.

## Why
KakaoPay sends the user back to the merchant's approval URL with `pg_token`. Endpoints such as `GET /kakaoPaySuccess?pg_token=` were not tagged `payment`.

## Reference
https://developers.kakaopay.com/docs/payment/online/single-payment

Refs #이슈번호

마지막 줄에는 고른 과제의 번호를 적어요. 번호는 과제 화면의 제목 옆에 #1234처럼 적혀 있어요. 여러 사람이 같이 쓰는 과제라면 Refs #번호, 혼자 맡은 과제라면 Closes #번호라고 적어요. 같이 쓰는 과제에 Closes를 쓰면 첫 PR이 반영될 때 과제가 닫혀 버려요.

다 적었으면 Create pull request를 눌러요. 내용을 빠뜨리고 올렸어도 괜찮아요. PR 화면에서 내용 오른쪽 위의 …를 누르고 Edit을 고르면 고칠 수 있어요.

주소가 github.com/owasp-noir/noir/pull/숫자로 바뀌었고, 초록색 Open 표시가 보여요. PR이 올라갔어요.

자동 검사 확인하기

PR 화면 아래쪽에 자동 검사 목록이 생겨요. 이 저장소에 처음 기여하는 계정은 관리자가 허락해야 검사가 시작돼요. 그래서 처음에는 기다리는 중이라고만 나올 수 있어요. 진행자가 차례로 허락할게요.

먼저 볼 검사는 Tag rule examples예요. 내 룰의 예시를 하나씩 돌려 보는 검사이고, 1분 안에 끝나요. 빨간 X가 뜨면 그 검사의 이름(또는 옆의 Details)을 눌러 기록을 열어 보세요. FAIL 뒤에 어느 파일의 무엇이 틀렸는지 한 줄로 나와요.

tests (1.22.0)이라는 검사도 같이 돌아요. Noir의 다른 테스트까지 전부 돌리는 검사라 5~8분쯤 걸려요. 이건 기다리지 않아도 돼요. 회색으로 Skipped라고 나오는 검사들은 룰 파일과 상관없어서 건너뛴 거예요. 룰 파일 말고 다른 파일을 고친 PR에서는 Tag rule examples도 건너뛰어요. 그때는 빨간 X가 없는지만 보면 돼요.

고칠 게 있으면 PR 화면의 Files changed 탭으로 가요. 파일 오른쪽의 …를 누르고 Edit file을 고르면 다시 고칠 수 있어요. Commit changes…로 저장하면 같은 PR에 반영되고 검사도 다시 돌아가요. PR을 새로 올릴 필요는 없어요.

Tag rule examples 옆에 초록색 체크가 떴어요. tests는 아직 돌고 있어도 괜찮아요.

막혔을 때

이런 게 보이면 이유 이렇게 해요
path_segment 'kakao_pay' contains a separator (/ - _ .) and can never match a single segment path_segment에 -, _, ., /가 들어간 단어를 넣었어요. 그 글자를 빼고 한 단어로 적어요. 주소가 /kakao-pay처럼 생겼다면 kakao와 pay로 나뉘니까, 둘 중 어느 걸 볼지 다시 정해요.
not tagged: POST /events (http) query:X-Example-Signature= match에 적은 예시에 태그가 안 붙었어요. 넣은 단어와 예시의 철자가 같은지 봐요. 단어를 all: 안에 있는 아래쪽 목록에 넣었다면 위쪽 목록으로 옮겨요. 웹훅 룰이라면 예시의 값에 type: header가 있는지 봐요.
tagged but listed under no_match: GET /kakaopay/login (http) no_match에 적은 예시에 태그가 붙어 버렸어요. 예시를 잘못 적었다면 예시를 고쳐요. 예시가 맞다면 넣은 단어가 너무 흔한 거예요. 더 구체적인 단어로 바꿔요.
기록에 YAML 오류와 줄 번호가 나와요 줄이 안 맞거나, 탭이 섞였거나, ]나 ,가 빠졌어요. 그 줄과 바로 윗줄을 위 예시와 한 글자씩 비교해 봐요.
typos라는 검사에 빨간 X가 떠요 넣은 단어를 영어 오타로 본 거예요. hight, ordr처럼 실제로 쓰는 이름도 걸려요. 오타가 맞으면 고쳐요. 실제 이름이라면 진행자에게 PR 번호를 알려 주세요.
검사가 시작되지 않고 기다리는 중이라고만 나와요 처음 기여하는 계정은 관리자가 허락해야 검사가 돌아가요. 기다리면 돼요. 진행자에게 PR 번호를 알려 주세요.

PR을 올린 뒤에는

  • 마무리 시간에 검사를 통과한 PR 한두 개를 그 자리에서 반영해 봐요. PR이 원본에 반영되는 걸 머지라고 해요. 나머지는 행사가 끝난 뒤 PR 댓글로 이야기를 이어 가요. GitHub에서 오는 알림 메일을 확인해 주세요.
  • 고쳐 달라는 댓글이 달리면 같은 PR에서 파일을 다시 고치면 돼요.
  • 머지되면 다음 Noir 버전에 내가 추가한 단어가 들어가요. 저장소 첫 화면의 기여자 그림에도 내 프로필이 올라가요.
