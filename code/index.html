목차

코드로 기여하기

Noir 코드를 직접 고쳐요. 오늘은 빌드하고 실패하는 테스트를 만드는 데까지를 목표로 하고, 수정은 행사 뒤에 이어서 해도 돼요.

준비물
브라우저(Codespaces), 또는 Crystal 1.19 이상
소요 시간
행사 뒤까지
결과물
Noir가 빌드되는 환경, 맡은 과제의 실패하는 테스트

시작하기 전에

Noir는 Crystal로 만들었어요. Crystal을 몰라도 아래 순서대로 하면 빌드와 테스트까지 돌릴 수 있어요.

준비하는 방법은 두 가지예요.

방법 이런 분께 준비에 걸리는 시간
브라우저에서 열기 (Codespaces) 아무것도 설치하고 싶지 않은 분, Windows를 쓰는 분 처음 열 때 몇 분
내 컴퓨터에 설치하기 평소 쓰는 편집기로 작업하고 싶은 분 설치 환경에 따라 달라요

어느 쪽이든 빌드와 테스트는 처음 한 번이 제일 오래 걸려요. 첫 빌드는 2~3분, 첫 테스트는 5분쯤 걸려요. 내 컴퓨터에 Crystal을 설치했고 더 가벼운 일부터 해 보고 싶다면, 아래의 시크릿 탐지 룰로 시작해도 좋아요.

설치 없이 시작하기

GitHub Codespaces를 쓰면 브라우저 안에서 편집기와 터미널이 열려요. Crystal과 필요한 도구가 이미 들어 있어요. Windows에서는 Crystal을 직접 설치하기가 번거로워서 이 방법을 권해요.

  1. Noir 저장소에서 오른쪽 위의 Fork를 눌러 내 계정에 복사본을 만들어요.
  2. 내 복사본 화면에서 초록색 Code 버튼을 누르고, Codespaces 탭에서 Create codespace on main을 눌러요.
  3. 몇 분 기다리면 편집기가 열려요. 처음에는 환경을 새로 만드느라 더 걸릴 수 있어요. 아래쪽 터미널에서 명령을 실행할 수 있어요.

이렇게 열었다면 아래 따라 하기의 1, 2단계는 건너뛰고 3단계 빌드하기부터 하면 돼요.

  • 컴퓨터 사양은 고르지 않아도 돼요. Noir를 빌드할 수 있는 4코어 머신이 자동으로 잡혀요.
  • GitHub 개인 계정에는 매달 무료 사용량이 있어요. 행사 시간 정도는 그 안에서 충분해요.
  • 다 쓴 뒤에는 codespaces 목록에서 지워 주세요. 켜 두면 무료 사용량이 계속 줄어요.

따라 하기

도구 설치하기

Codespaces로 열었다면 이 단계와 다음 단계는 건너뛰어요. 이미 다 준비돼 있어요.

macOS라면 Homebrew로 설치해요.

brew install crystal just

Ubuntu나 Debian이라면 Crystal 설치 스크립트를 쓰고, 빌드에 필요한 라이브러리도 같이 설치해요.

curl -fsSL https://crystal-lang.org/install.sh | sudo bash
sudo apt install -y libyaml-dev libzstd-dev zlib1g-dev pkg-config just

다른 환경은 Crystal 설치 안내를 참고하세요.

crystal --version과 just --version을 실행하면 각각 버전이 나와요.

내 계정으로 복사해서 내려받기

Noir 저장소에서 오른쪽 위의 Fork를 눌러요. 내 계정에 복사본이 생겨요. 이걸 포크라고 해요. 그 복사본을 내 컴퓨터로 내려받아요.

git clone https://github.com/내아이디/noir
cd noir
shards install

shards install은 Noir가 쓰는 라이브러리를 받아 오는 명령이에요.

lib/ 폴더가 생겼고, 오류 없이 끝났어요.

빌드하기

just build

처음에는 시간이 좀 더 걸려요. 끝나면 bin/noir가 생겨요. 저장소에 들어 있는 예제 코드를 스캔해서 잘 되는지 확인해요.

./bin/noir scan spec/functional_test/fixtures/crystal

엔드포인트 목록이 나와요. 이제 내가 고친 코드로 Noir를 돌려 볼 수 있어요.

테스트 돌리기

just test

테스트 전체를 실행 파일 하나(bin/noir_spec)로 만든 다음 실행해요. 만드는 데 시간이 제일 많이 들어요. 그래서 한 번 만든 뒤에는 필요한 테스트만 골라서 돌려요.

./bin/noir_spec -e hono

-e 뒤에 이름 일부를 적으면 그 이름이 들어간 테스트만 돌아가요. 0 examples라고 나오면 통과한 게 아니라 맞는 이름이 없었다는 뜻이에요.

예제 코드 폴더 하나만 검사하고 싶을 때는 이름이 조금 달라요. 폴더 경로를 대괄호로 감싸면 엔드포인트 개수 검사가 돌고, :: 뒤에 주소를 적으면 그 주소의 검사가 돌아요.

./bin/noir_spec -e "[fixtures/php/php/]"
./bin/noir_spec -e "::/get.php"

예제 코드와 기대 결과(.yml)만 고쳤다면 다시 만들 필요가 없어요. 실행할 때 읽어 오거든요. Noir 코드(src/)를 고친 뒤에만 just spec-build로 다시 만들어요. 한 번에 몇 분씩 걸려요.

실패 없이 끝났어요. 고치기 전에 다 통과하는 걸 확인해 둬야, 나중에 실패했을 때 내가 고친 것 때문인지 알 수 있어요.

과제 맡기

과제 목록에서 하나를 골라 "제가 할게요"라고 댓글을 남겨요. 이미 댓글이 달려 있으면 다른 과제를 골라 주세요. 과제마다 문제가 생기는 짧은 코드, 지금 나오는 결과, 나와야 하는 결과가 적혀 있어요. 과제에 나오는 noir scan .은 방금 빌드한 bin/noir로 실행하면 돼요.

과제에 붙은 라벨을 보고 골라요. 어디를 고치는지는 과제의 "고칠 곳"에 적혀 있어요.

라벨 뜻
🟡 medium 오늘 실패하는 테스트까지 만들 수 있어요. 빠르면 수정까지 가요.
🔴 hard 어떻게 풀지부터 이야기해야 하는 과제예요. 행사 뒤까지 이어져요.

목록에 없는 일도 환영해요. 써 보고 제보하기에서 직접 찾은 문제를 고쳐도 되고, 새 출력 형식이나 새 프레임워크 지원처럼 직접 정한 일이라면 먼저 이슈를 열어 무엇을 할지 적어 주세요.

엔드포인트를 찾는 부분을 고칠 때는 순서가 있어요.

  1. 문제가 드러나는 예제 코드를 spec/functional_test/fixtures/ 아래에 넣어요. 과제에 적힌 폴더에 파일을 추가하면 돼요.
  2. 나와야 하는 엔드포인트를 spec/functional_test/testers/의 .yml 파일에 적어요. 파일 맨 위 counts의 endpoints 숫자도 늘어난 만큼 고쳐요.
  3. 테스트를 돌려서 실패하는 걸 확인해요. 이때는 실패하는 게 맞아요.
  4. 코드를 고쳐서 테스트를 통과시켜요.

PHP 과제라면 2번에서 이렇게 적어요. type에는 query, form, json, header, cookie, path 중 하나가 와요.

  - url: "/confirm.php"
    method: "POST"
    params:
      - {name: "orderId", type: "json"}
      - {name: "amount", type: "json"}
      - {name: "coupon", type: "form"}

3번에서는 이런 줄이 나와요. 무엇이 빠졌는지 그대로 알려 줘요.

MISSING PARAM [orderId] on [POST::/confirm.php] in tester: fixtures/php/php/

오늘은 3번까지만 해도 충분해요. 실패하는 테스트가 있으면 행사 뒤에 이어서 고치기 쉬워요.

저장소가 어떻게 생겼는지, 새 기능은 어디에 넣는지는 AGENTS.md에 정리돼 있어요. 코드를 읽기 전에 이 문서부터 읽어 보세요.

맡은 이슈에 내 댓글이 달렸어요. 고칠 파일이 어디 있는지도 찾았어요.

고치고 PR 올리기

작업할 브랜치를 하나 만들어서 고쳐요. 브랜치 이름은 내 과제에 맞게 지어요.

git checkout -b fix/php-input-json-body

다 고쳤으면 코드 모양을 검사하고 테스트를 다시 돌려요.

just check
just test

둘 다 처음에는 몇 분씩 걸려요. just check가 알려 준 것 중 자동으로 고칠 수 있는 건 just fix가 고쳐 줘요. 다 통과하면 저장하고 올려요.

git add -A
git commit -m "fix(php): read JSON body keys from php://input"
git push origin fix/php-input-json-body

GitHub에서 내 복사본 화면으로 가면 Compare & pull request 버튼이 보여요. 눌러서 PR을 올려요. 내용에는 뭘 왜 고쳤는지 적고, 마지막 줄에 Closes #1234처럼 맡은 과제 번호를 적어요. 한국어로 써도 돼요.

PR이 올라갔고 자동 검사가 시작됐어요. 처음 기여하는 계정은 관리자가 허락한 뒤에 검사가 돌아가요.

시크릿 탐지 룰

이 과제는 내 컴퓨터에 Crystal을 설치한 분께 권해요. Noir용 Codespaces 안에서는 다른 저장소로 올리는 게 막혀 있을 수 있어요.

Noir는 엔드포인트를 찾으면서, 코드에 실수로 적어 둔 API 키나 토큰도 같이 찾아요. 이걸 찾는 규칙은 noir-passive-rules라는 다른 저장소에 들어 있어요. 국내 서비스의 키 모양은 아직 거의 없어요.

규칙 하나는 이렇게 생겼어요.

id: stripe-webhook-secret
info:
  name: Detect Stripe Webhook Secret
  author: [owasp noir team]
  severity: high
  description: Detects Stripe webhook signing secrets, which allow forging webhook events
  reference: ['https://docs.stripe.com/webhooks#verify-events']
matchers-condition: or
matchers:
  - type: regex
    patterns:
      - '\bwhsec_[A-Za-z0-9]{32,}'
    condition: or
category: secret
techs: ['*']

기여는 세 단계예요.

  1. secrets/ 폴더에 규칙 파일을 추가해요. 키가 어떻게 생겼는지는 그 서비스의 공식 문서에서 확인해요.
  2. spec/secrets_spec.cr에 테스트를 추가해요. 잡혀야 하는 글자와 잡히면 안 되는 글자를 각각 적어요.
  3. crystal spec/secrets_spec.cr로 테스트를 돌리고 PR을 올려요.

테스트에 넣는 가짜 키는 한 번에 쓰지 말고 "whs" + "ec_" + "A" * 32처럼 쪼개서 이어 붙여야 해요. 통째로 쓰면 GitHub가 진짜 키로 착각해서 올리지 못하게 막아요. 자세한 방법은 그 저장소의 AGENTS.md에 순서대로 나와 있어요.

AI 도구를 쓴다면

두 저장소 모두 AI 도구가 읽는 안내 파일(AGENTS.md)이 있어서, Claude Code나 Codex 같은 도구로 작업하기 좋아요. 다만 PR을 올리는 사람은 여러분이에요. AI가 고친 것이라도 뭘 왜 바꿨는지 설명할 수 있어야 하고, 테스트가 통과하는지 직접 확인한 다음에 올려 주세요.
